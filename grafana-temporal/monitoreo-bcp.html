2. Fuente de métricas (OpenMetrics)

Un scrape a https://metrics.temporal.io/v1/metrics con API key (rol Metrics Read-Only). Si el overview D01 ya pinta temporal_cloud_v1_*, el scrape está hecho. Intervalo 60 s: Cloud agrega a 1 minuto; scrapear más seguido no da más resolución y sube DPM / puede pegar el rate limit del endpoint (≈ 180 req/hora por account).

Las series v1 ya son rates por segundo (ventana 1 min) o gauges. En dashboards y alertas no usar rate() / increase() / irate(). Usar sum, avg, clamp_min, avg_over_time, sum_over_time.

Ejemplo de job Prometheus (si no es la integración Grafana Cloud). Ajustar namespaces al inventario; omitir el param para scrapear todo el account:

scrape_configs:
  - job_name: temporal-cloud
    scrape_interval: 60s
    scrape_timeout: 30s
    honor_timestamps: true
    scheme: https
    metrics_path: /v1/metrics
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/temporal-metrics-api-key
    params:
      namespaces:
        - apoq-prod
        - nrem-prod
    static_configs:
      - targets: ["metrics.temporal.io"]
  • El nombre del job (temporal-cloud) entra en up{job="temporal-cloud"}. En Grafana Cloud suele ser otro. En Explore: up{job=~".*temporal.*"} y copiar el valor exacto a la alerta de scrape.
  • Labels opt-in (temporal_activity_type, worker deployment) no en el scrape 24×7. Job de diagnóstico aparte.
  • temporal_cloud_v1_billable_action_count es de alta cardinalidad (namespace × workflow type × action_type). Si D05 sale vacío y D01 sí pinta Actions, el relabel puede estar droppeando esa métrica.
  • Retention prod recomendada ≥ 90 días (totales 30d de D05 y SLO mensual).
  • Los percentiles v1 no se re-agregan entre namespaces ni a ventanas más largas.

Si en Explore aparece temporal_cloud_v0_*, el datasource sigue en el PromQL legado. D02/D05 no funcionan contra v0. Apagado: 5 oct 2026.

3. D01 — overview (instalado)

Es el dashboard que Grafana Cloud instala con la integración Temporal (mixin OpenMetrics). Exploración de plataforma: requests, backlog, workflows, activities, pollers, cuotas, schedules, latencias Start/Signal, billable, TRU.

No es tablero de guardia, no trae alertas, no es tablero de una app.

Validar (15 min)

  1. Explore o un panel: queries temporal_cloud_v1_*, no v0.
  2. Scrape ~60 s.
  3. Variable temporal_namespace lista los namespaces reales. Si no salen, el job filtra otros nombres o el account no los tiene.
  4. Con un namespace prod: hay datos en Open Workflows, Failed, Task backlog, Actions, Service requests. Vacío en Activities = puede no haber activities en la ventana. Vacío en TRU = on-demand (normal).
  5. No usar p95/p99 de Start/Signal como paging si hay pocos requests/min.

Orden de lectura en incidente (si aún no está D02)

  1. Failed workflows / failed by type y task queue.
  2. Task backlog + no_poller_tasks_count.
  3. Sync match rate.
  4. Resource exhausted + actions/operations/RPS throttled vs *_limit.
  5. Service errors en Start / Signal / SignalWithStart.
  6. Replication lag solo si el namespace es HA multi-región.

no_poller y backlog son señales de Cloud (el matching no encuentra poller / hay cola). No diagnostican el worker en AKS; eso es el corte SDK.

  1. Desmarcar All y elegir un namespace (prod vs prod, no mezclar).

Métricas D02 y D05 (detalle)

Prefijo temporal_cloud_v1_. Cloud publica ya agregado a 1 minuto: las rate son eventos/s (media del minuto); los gauge son valor puntual. No usar rate() / increase(). Un 0.5 en una rate ≈ 30 eventos en ese minuto. Los bursts de pocos segundos se diluyen: por eso se alerta throttle/exhaustion, no solo el % medio del límite.

6. Cómo importar un JSON en Grafana

  1. Grafana → Dashboards → New → Import.
  2. Upload d02-slo.json o d05-finops.json (no pegar el YAML de alertas aquí).
  3. Datasource: el mismo Prometheus que pinta el Temporal overview (D01).
  4. Import. Comprobar uid (si ya existe un dashboard con ese uid, Grafana pedirá overwrite o cambiar uid).
  5. Arriba: Namespace = All o un namespace concreto. Refresh 1m.
  6. Opcional: folder “Temporal Cloud”, star para guardia (D02) o Finanzas (D05).

Si al importar pide un datasource que no existe, crear/seleccionar el Prometheus del scrape OpenMetrics. Los paneles usan ${DS_PROMETHEUS}.

7. Cómo configurar alertas

El archivo alertas-catalogo.yaml es un borrador Prometheus / Grafana Alerting. No se “importa” como dashboard. Hay que crear reglas (a mano o vía provisioning) sobre el mismo datasource de D01.

Antes de pegar exprs. (1) Sustituir job="temporal-cloud" por el job real. (2) Sustituir temporal_namespace=~"apoq-prod|nrem-prod" por los namespaces de guardia, o quitar el filtro para alertar todos (más ruido en cert). (3) Acotar TemporalCloudWorkflowFailRate a los temporal_workflow_type críticos; si no, pagina types de prueba. (4) Apagar TemporalCloudReplicationLag si no hay HA.

7.1 Contact points y ruteo

  1. Alerting → Contact points. Tres destinos, no uno:
    • guardia-p1 — PagerDuty / Opsgenie / teléfono. Solo P1.
    • sre-p2 — Slack/Teams canal SRE + PO. P2.
    • finops-p3 — ticket / canal Finanzas. P3. Nunca paging.
  2. Notification policies. Árbol por label severity:
    • severity=p1 → guardia-p1 (y opcional copia a Slack).
    • severity=p2 → sre-p2.
    • severity=p3 → finops-p3.
  3. Todas las reglas del YAML ya ponen severity: p1|p2|p3 y layer: cloud.
  4. Mute timings para TemporalCloudStartSilence: America/Lima 20:00–08:00 y fines de semana, o la alerta dispara todas las noches. El resto de P1 no se silencian de noche.
  5. Grupo por temporal_namespace para no recibir 20 páginas del mismo namespace.

7.2 Crear una regla en Grafana Alerting (recomendado para empezar: las 5 P1)

  1. Alerting → Alert rules → New alert rule.
  2. Folder p.ej. temporal-cloud.
  3. Query: datasource Prometheus de D01. Pegar la expr del YAML (sin el for).
  4. Condition: umbral ya va en la expr (> 0.01, == 0, etc.). En Grafana 10+: “Alert if” / reduce last / IS ABOVE 0 si la expr ya es booleana 0/1; si la expr ya compara, usar “WHEN last() OF A IS ABOVE 0” sobre una query que devuelve 1 cuando dispara, o pegar la expr y umbral 0 con “classic condition”. Lo más simple: expr que devuelve series que cumplen, y “Has no value” no alerta; “Alert if query is not empty” / threshold > 0 según UI.
  5. En la práctica Grafana Cloud: pestaña Set alert evaluation behavior:
    • Pending period = el for del YAML (5m, 10m, 2m, 3m…).
    • Evaluate every = 1m (alineado al scrape).
  6. Labels: severity=p1, layer=cloud. Summary/description de annotations (Grafana usa {{ $labels.temporal_namespace }} igual que Prometheus).
  7. Save. Probar con Preview / Explore pegando la misma expr.

Orden de creación: las cinco P1 primero. Luego P3 de D05. P2 cuando el ruido de P1 esté controlado y existan types críticos.

7.3 Grafana Cloud: mimir / ruler (opcional)

Si hay provisioning GitOps, el YAML se puede cargar como Prometheus rule group (nombres de grupo temporal-cloud-scrape y temporal-cloud-prod). Ajustar datasource/tenant. No mezclar con el YAML v0 de Temporal (temporal_cloud_action_costs_alerts.yaml).

7.4 Comprobar que no están ciegos

  1. Explore: la expr P1 de error rate debe devolver nada en calma, o valores < 0.01.
  2. Forzar una prueba: expr vector(1) 1m a un contact point de prueba, no a PagerDuty real.
  3. Confirmar que up del job es 1. Si up no existe, la P1 de scrape nunca dispara y el resto puede quedarse en “sin datos” = verde falso.

Datos OpenMetrics llegan con ~1–3 min de retraso. El for ya incluye holgura; no bajar P1 a 0s.

9. Cómo usarlas en guardia y Finanzas

Turno de guardia

  1. D02 en un monitor. Namespace de prod (no All si hay cert ruidoso).
  2. Página P1 → abrir D02 filtrado al temporal_namespace de la alerta.
  3. Mapa rápido:
    • Scrape down → no mires workflows; arregla métricas.
    • Error rate → ¿Cloud acepta Start/Signal?
    • Exhausted / throttle → cuota / burst.
    • No poller → workers / TQ, no “Temporal Cloud caído”.
  4. Si hace falta el mapa completo: D01. Si hace falta el type de negocio: hoy Explore por temporal_workflow_type; mañana D03/D04.
  5. P2 de fail-rate: confirmar que el type es de negocio, no un workflow de prueba.

Review FinOps (semanal)

  1. D05, 7d, un namespace prod a la vez.
  2. Totales vs factura Temporal (fuera de Grafana).
  3. Top 20 + % heartbeat/retry.
  4. P3 de baseline 7d: ¿deploy, retry storm, TRU ocioso?
  5. Actions > 80% del límite: pedir headroom o bajar APS, no esperar al throttle P1.

Falsos verdes / falsos rojos

  • Error rate 0% y Start/s = 0: cliente parado o Cloud inalcanzable. Por eso existe StartSilence (P2) y el piso 0.1/s en P1.
  • % de action_limit verde + throttle P1: la rate de 1 min suaviza bursts.
  • D01 verde + no poller P1: worker/PE caído; Cloud solo ve matching.
  • Fail-rate P2 en compensación esperada: filtrar types.
